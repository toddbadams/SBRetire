## 1. Maximum Sustainable Budget: per-path threshold bisection, £0 to a doubling upper bound, £1/month tolerance

With one `RandomInputs` reused for every candidate (Common Random Numbers), each Path's success is monotone non-increasing in the Budget, so each Path has a threshold T_i — the largest Budget at which it is Successful. All Paths are bisected together by giving each its own candidate budget in one vectorised engine run: lower bound £0 (feasible for every completed-by-death Path), upper bound starting at 2 × the configured Budget (£1,000 if zero) and doubling until every completed-by-death Path fails, capped at £1,000,000/month (Paths still Successful there take T = cap and are flagged). Bisection stops when every bracket is ≤ £1/month; T_i is the feasible end. Paths with someone alive at the Horizon can never be Successful and have no threshold. For a target p*, B* is the ⌈p*·N⌉-th largest threshold, so the Conservative Success Rate at B* is ≥ p*; if fewer Paths have thresholds, the target is reported infeasible rather than given a number. Each result reports B* per month and per year, the estimated success probability with its standard error (denominator: all Paths), the unresolved fraction, the tolerance, convergence and the iteration count. (F-010)

**Why**: SPEC §14 asks for bisection on the Budget with CRN, explicit bounds verified feasible/infeasible, a documented expansion strategy and a currency tolerance. Because the rate at budget B is exactly the share of thresholds ≥ B, bisecting thresholds per Path is the same bisection resolved for every Path at once: one search (~20 engine runs) serves every confidence level, instead of a separate scalar bisection per target. Taking the feasible end and the ⌈p*·N⌉-th threshold never overstates sustainability. £1/month matches SPEC's example and costs only two runs more than £5; bounds and tolerance are fixed constants echoed in the output rather than configuration.

## 2. Return Search: per-path minimum return, fixed bounds −50 % … +50 %, 0.01 pp tolerance

For a fixed Budget (the configured one unless given), each completed-by-death Path has a minimum fixed annual effective return R_i at which it is Successful; all Paths are bisected together with a per-path return in one vectorised engine run per round, between fixed bounds −50 % and +50 % a year, to a tolerance of 0.0001 (0.01 percentage points), taking the feasible upper end. Paths that fail even at +50 %, and Paths with someone alive at the Horizon, have no solution in range (R = +∞); Paths Successful even at −50 % take R = −50 % and are flagged. For a target p*, the required return r* is the ⌈p*·N⌉-th smallest R_i, confirmed by one run at r* (exact rate, SE with denominator all Paths, unresolved share). Fewer finite thresholds than needed → "no solution within bounds" (no number); r* at −50 % → reported as "≤ −50 %", not converged. Monotonicity — success never decreasing in the return — follows from the never-negative balance and return-on-opening-balance convention and is verified by a test over a grid of returns, as SPEC §13 requires. (F-011)

**Why**: SPEC §13 asks for a bracketed search with defined bounds, a stopping tolerance, explicit no-solution behaviour and a verified monotonicity assumption. Mirroring the budget search (§1) gives one search for every target with Common Random Numbers. Fixed wide bounds are simpler to document than an expanding bracket and keep plans whose income does most of the work off the lower bound; 0.01 pp is finer than any planning use needs at ~14 rounds. Return results are model outputs under fixed-return assumptions, not forecasts.


## 3. End-of-Life Reserve: an opt-in stricter success test, searched with the same per-path thresholds

`budget.end_reserve_months` (R, whole months, default 0 = off). A Path meets the End-of-Life Reserve target when it is Successful (simulation-conventions §7) **and** its balance at Household End is at least the Required End Balance R × B × I_d: B the Budget in today's GBP per month (during the search, the candidate budget), I_d that Path's Inflation Index at its Household End month d — the full Budget, not the survivor-reduced spending. A Path that ends below its reserve counts as Failed for the reserve metrics; Unresolved Paths are unchanged and never succeed. The Maximum Sustainable Budget leaving the reserve uses §1 unchanged: a higher budget never leaves a higher final balance and needs a higher reserve, so each Path still has one threshold (verified by a test). With R > 0, `run` adds a summary line, a second budget table and `lifestyle_reserve_results.csv`; every V1 output is identical to R = 0. Options left at their default are omitted from the Config Hash (configuration §7), so V1 configs keep their hash. (F-019)

**Why**: the user asked how much the household can spend and still leave 12 months' budget in savings at the second death, and chose 12 × the monthly Budget in today's money, inflated to that date. Counting a short-of-reserve Path as Failed keeps the three-way split and both rates meaningful, and never overstates sustainability. Keeping it opt-in and beside the V1 table leaves the SPEC §14 result untouched.
